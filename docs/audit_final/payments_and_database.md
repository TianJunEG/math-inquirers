## Findings

### High
**F1. Live database is not migrated; Stripe and shop paths cannot work today.** Evidence: live functions are service_begin_hitpay, service_attach_hitpay, service_mark_hitpay_paid (HitPay, retired); no service_begin_payment, service_attach_session, service_mark_paid, service_mark_session_failed; payments has no provider_ref, provider_payment_ref, provider_attempt columns; no entitlements, delivery_log, product_interest tables; only migration recorded is 20261022044929 portal_tables. Impact: with the Worker deployed, create-checkout would 502 and the webhook would answer 502 for every paid event (Stripe retries, money taken, enrolment never confirmed). Fix: apply stripe_migration.sql, delivery.sql, product_interest.sql (owner approval), re-run advisors and the grant query, then do a Stripe test-mode payment end to end. Until then keep PAYMENT_MODE = paynow_manual (the code defaults to it). Not applied by me.

### Medium
**F2. Late or duplicate Stripe payment silently ignored: possible double payment goes unflagged.** schema.sql:386 / stripe_migration.sql service_mark_paid returns already_paid with no comparison of provider_payment_ref; stripe-webhook.js:182 only logs mismatch, cancelled and not_found. Case: parent pays by manual PayNow, admin ticks paid, then a still-open Stripe session is also paid (or two sessions paid after expiry/retry). Second payment is never reported. Fix: in service_mark_paid, if status paid and provider_payment_ref differs from p_payment_intent (and is not null), return 'duplicate_payment'; add it to the NEEDS OWNER ATTENTION list. Also cancel/expire the open Stripe session when admin_mark_paid or cancel_my_enrolment runs (or at least log).
**F3. service_mark_paid flips refunded or failed payments back to paid.** schema.sql:384-391 only tests status = 'paid'. A late event for a payment the owner set to 'refunded' makes it 'paid' and re-confirms nothing (enrolment cancelled) but destroys the refund record. Fix: only proceed when status in ('pending','cancelled'); return 'not_payable:<status>' otherwise and log it.
**F4. Seats can be hoarded: reservations never expire.** schema.sql:270-293: pending_payment counts against capacity indefinitely; a signed-up parent can reserve up to 6 seats (6 children, 6 groups at 8 seats). Many throwaway accounts block every group (6 groups x 8 seats). Email confirmation is on in the client flow but I could not verify the project Auth settings. Fix: expire pending_payment after N days (cron or check inside enrol_child), cap open reservations per parent, require confirmed email server-side.
**F5. Owner payment decisions not implemented.** owner_decisions.md items 1 and 5 (prorated mid-year fee, 5% full-term discount, three instalments, schedule shown) have no support: payments is one row per enrolment with one amount_cents = groups.fee_cents; app.js:186 shows "for all 10 lessons" and enrolCard says "Beta: 5 weeks". Fine for the beta, not for term launch. Needs design (payment plan table, per-instalment checkout, webhook mapping per instalment).
**F6. Shop (soft copy) webhook path does not verify the amount paid.** stripe-webhook.js:165 and delivery.js maybeHandleShopOrder grant links for any paid session whose metadata.mi_items lists a manifest product; amount_total is never compared with a price. My test: amount_total 1 with mi_items passes the paid check (stopped only by the manifest lookup). There is no server-side shop checkout in the repo (grep mi_items: only delivery code and tests; website shop shows "https://checkout.stripe.com/..." placeholders), so today safety rests on the owner creating Payment Links with correct metadata and prices. Fix: a price table (product_id to cents, SGD) checked against amount_total/currency before granting; or a server-side shop checkout like the enrolment one.
**F7. Child PIN: weak against a targeted guess, and lockout is a nuisance attack.** schema.sql:219-242: PIN is 4 to 6 digits (4 digits = 10,000 values), 5 tries then 15 minutes, per child, no per-IP limit, counter resets on lock. Attacker needing family code (6 of 31 chars) and child name: about 5 days expected for a 4-digit PIN. Same attacker can keep a known child locked out indefinitely. Locked children return faster than unlocked wrong guesses (no crypt call), a small timing oracle that a code+name pair exists. Fix: require 6-digit PIN or exponential back-off (15 min, 1 h, 24 h), include p_name in a per-family-code failure counter, run the dummy crypt in the locked branch too, rate-limit at the edge (Cloudflare rule on /rest/v1/rpc/child_sign_in).
**F8. Child sign-in is client-side only.** child.js:19 stores {id,name,level} in sessionStorage after a successful RPC; there is no server session or token. Today practice is a placeholder and practice_attempts has no write path (no insert grant), so no data is exposed. The moment practice results are saved, a child identity is forgeable. Fix before any practice write: return a signed short-lived token from child_sign_in (or a service-side endpoint) and verify it server-side.
**F9. Checkout idempotency key can pin a parent to a dead or rejected session.** stripe-create-checkout.js:124: key mi-checkout-<payment>-<attempt>. (a) If service_attach_session failed (non-fatal, line 131), provider_ref stays null, so the later expired event returns 'ignored' (provider_ref distinct from session) and attempt is not bumped: Stripe replays the cached expired session for up to 24 h. (b) Stripe rejects the same key with changed parameters (changed customer email or group name) with 400, shown as a generic 502 to the parent. Fix: in service_mark_session_failed bump attempt when provider_ref is null; include a hash of the parameters in the key; retry once with attempt+1 on a 400 idempotency error.
**F10. Interest form brake can be abused.** interest_requests.sql: global cap 300 per hour means a bot can lock every real parent out ('busy'); "already_received" lets anyone test whether a phone or email already submitted. Fix: per-IP limit at the edge, return the same status for new and repeat.

### Low
- L1. stripe-webhook.js:153 reads the whole body before verifying (50 MB took 0.6 s); add a Content-Length cap (e.g. 1 MB) before request.text().
- L2. create-checkout has no rate limit (each call does an auth round-trip plus an idempotent Stripe call). Add a Cloudflare rate rule on /api/*.
- L3. service_mark_paid trusts session.client_reference_id without comparing session id to provider_ref; safe because payment id is a UUID in a signed event, but a mismatch should be logged.
- L4. gen_code uses random() (not a CSPRNG) for family codes and payment references (schema.sql:7-16). Use gen_random_bytes from pgcrypto.
- L5. Success page banner (app.js:262) shows "Thanks" for any ?paid= value; cosmetic. It correctly does not mark anything paid from the URL.
- L6. delivery_log grows with every failed token attempt (rate-limited per IP hash only; rotating IPs inflate it). Page missing CF-Connecting-IP disables the limit (delivery.js: null ip). Fine behind Cloudflare.
- L7. finish_setup.sql still creates the HitPay functions and grants; its header says to run stripe_migration.sql after. Folded into F1; prefer one clean install path (schema.sql + policies.sql already contain Stripe).
- L8. Security headers: website/dist/_headers has CSP, nosniff, frame DENY. The checked-in dist has no /portal/ (built without portal), and the portal CSP must allow the Supabase origin and https://checkout.stripe.com redirects (top-level navigation is fine). Verify the built portal output before launch.
- L9. Live advisors: rls_enabled_no_policy (admins, deletion_requests, interest_requests) is intended (no direct access); the two anon-callable SECURITY DEFINER lints are child_sign_in and submit_interest_request (judged below).

## Judgement of the SECURITY DEFINER lints (live)
All 29 public functions: search_path pinned; no PUBLIC execute; internal helpers (_require_parent, gen_code, handle_new_user, forbid_mutation) not granted to anon/authenticated. anon: child_sign_in (by design, see F7) and submit_interest_request (validated, honeypot, caps, see F10). authenticated: parent functions all derive identity from auth.uid() via _require_parent (no caller-supplied parent id); admin_* check is_admin() first; is_admin() and group_fill() are harmless. Verified in the rolled-back test: another parent cannot cancel or enrol with someone else's child (not_found / cannot_cancel_contact_us), non-admin gets forbidden, authenticated cannot call service_* (permission denied), direct UPDATE on payments/groups/parents.family_code denied, pin_hash not selectable, other parent update touches 0 rows, anon cannot read parents, 5 wrong PINs lock sign-in, delete_my_data removes the login. RLS enabled on all 10 live tables; policies match policies.sql exactly.
